**HORKOS** (ὅρκος) — клятва и кара за её нарушение. Это единственный процесс в экосистеме
AIMarket, который держит приватный ключ, авторизованный в `AIMarketEscrow.authorizedHubs`.
Он существует ровно для того, чтобы этот ключ **не** держал Hub.

**Адрес:** `0xBE0bBE44cceCfEb048dd53f601C37525a3D6C5f1` · **Сеть:** Base mainnet (8453) ·
**Эскроу:** `0x12Db8FAC81E5999D2f2087B79e38951571562CF2` · **Хост:** отдельная машина,
доступная с хоста Hub только через обратный SSH-туннель.

Не на той же машине, где Hub: общий хост превратил бы фразу «ключ не входит в процесс Hub» в
предложение вместо границы — тот, кто получил доступ к докеру, получил бы оба.

## Что он подпишет

Ровно одно: каноничный вызов `debitChannel(bytes32,uint256,bytes32,uint256,bytes)`, селектор
`0xf7becd80`, на один закреплённый эскроу-контракт, в одной закреплённой сети, с `value == 0`.
Больше ничего: ни `settleChannel`, ни `transfer` токена, ни `setHubAuthorization`, ни
развёртывание контракта, ни другую сеть.

Полномочие на **сумму** даёт не Hub. Его даёт EIP-712 подпись depositor'а, которая проверяется
здесь заново — против состояния платёжного канала, прочитанного этим процессом самостоятельно,
и с подстановкой **собственного адреса** в поле `hub`, как это делает контракт. Подпись,
выписанная для другого хаба, на другом nonce или кем-то, кто не является depositor'ом канала,
будет отклонена.

## Зачем отдельный подписант, а не ключ в Hub

`AIMARKET_ESCROW_SUBMIT_STRATEGY=external` выносит ключ из процесса Hub — и сам по себе даёт
мало. Hub присылает `{to, data, chainId, gas, value}`, и наивный подписант подписал бы что
угодно: скомпрометированный Hub с bearer-токеном попросил бы `USDC.transfer(атакующий, всё)`.
Поэтому вся ценность в отказах, и они перечислены как правила R1–R26 в `escrow_signer/`.

Остаточный риск, который не закрывает никакой подписант, прямо: **скомпрометированный Hub
всё ещё может собрать деньги за невыполненную работу — в пределах лимитов и только по тем
суммам, которые покупатели уже подписали.** Все поля, которые проверяет контракт, входят в
дайджест depositor'а, поэтому такая заявка неотличима от честной. Риск уменьшается меньшими
лимитами и подписью на каждый вызов вместо подписи заранее.

## Развёртывание

```
scp -r escrow-signer/ signer-host:/root/escrow-signer/
cp .env.example .env      # на хосте, chmod 600, вписать ключ и токен
docker compose up -d --build
curl -s localhost:9500/health     # {"ok":true,"ready":true,...}
```

Затем на хосте **Hub**:

```
cp deploy/escrow-signer-tunnel.service /etc/systemd/system/
systemctl enable --now escrow-signer-tunnel

cd /root/claudecode/aicom && ./scripts/deploy_hub_rebuild.sh --no-build \
  --set AIMARKET_ESCROW_SUBMIT_STRATEGY=external \
  --set AIMARKET_ESCROW_SIGNER_URL=http://127.0.0.1:9500/sign \
  --set AIMARKET_ESCROW_SIGNER_TOKEN="$(cat /root/.escrow-signer-token)" \
  --set AIMARKET_ESCROW_SUBMIT_CONFIRM=i-understand-this-moves-funds
```

Сначала всегда `plan`: он собирает настоящий calldata и прогоняет его через `eth_call` по
живому состоянию, то есть отвечает «прошло бы это сейчас?» без транзакции.

```
docker exec modelmarket-hub python -m aimarket_hub.escrow_bridge.cli plan
docker exec modelmarket-hub python -m aimarket_hub.escrow_bridge.cli submit --yes
```

Четвёртая ступень допуска сделана намеренно: ни в одной стратегии Hub не отправляет
транзакции из пути запроса, поэтому регулярный расчёт — это таймер, вызывающий
`submit --yes`, а не фоновый поток.

## Эксплуатация

- `GET /health` — готовность, адрес и причина отказа, если он есть. Без записи в книги.
- `GET /status` — действующие лимиты и состояние книг.
- `GET /receipt/<receipt_id>` — авторитетный ответ на вопрос «что этот сервис действительно
  отправил». Hub считает возвращённый хеш доказательством; здесь это можно сверить.
- Сервис стартует **в состоянии отказа** и остаётся в нём, пока не сойдутся книги, пока
  цепочка не подтвердит, что он авторизованный хаб, пока не совпадёт domain separator и пока
  каждая незакрытая запись не будет классифицирована по данным цепочки. Остановленная очередь
  лучше неучтённой подписи.

**Этот адрес ещё и получатель.** `settleChannel` платит `ch.hub`, то есть выручка копится
здесь, а не в казне. Перевод в казну — отдельное осознанное действие оператора.

## Лимиты

Все — в целых базовых единицах USDC (6 знаков). Каждый обязателен: отсутствующее, нулевое или
отрицательное значение не даёт сервису запуститься, а «без лимита» пишется словом `unlimited`
и объявляется при каждом старте. Лимита «на проход» намеренно нет: в формате запроса нет
идентификатора прохода, а «проход», выведенный из паузы между запросами, сбрасывается
темпом обращений. Этот лимит остаётся на стороне Hub.

Лимиты по количеству не дублируют денежные: выжигание квитанций и перебор nonce не стоят ни
одного USDC и ограничены только счётчиками. `SIGNER_CAP_FEE_WEI_24H` — третья, отдельная
величина: денежные лимиты считаются в токене, а расходуется ETH этого ключа.

## Тесты

```
python -m pytest escrow-signer/tests -q      # 95 тестов
```

`tests/test_wire.py` импортирует собственный класс `ExternalSigner` из Hub и гоняет его через
настоящий сокет — включая проверку, что **ни один маршрут никогда не отвечает 3xx**: `urllib`
идёт по перенаправлению вместе с заголовком `Authorization`, и лишний слэш превратился бы в
утечку токена. `tests/test_policy.py` — таблица отказов, где каждый случай проверяет, что
ничего не подписано и ничего не отправлено, а не только код ответа.
